# ТЗ: поле «Счёт» у транзакции

Счёт — это откуда потрачены деньги («Тинькофф», «Наличные»). Поле-пустышка:
в расчётах, ленте и фильтрах не участвует, это часть описания траты.
Отображается только в подробной карточке транзакции.

Статус: согласовано, к реализации.

## Принятые решения

### Модель данных

- Счета — **отдельный справочник** `Account` (таблица, как `Category`), а не
  строка внутри транзакции. Причина: нужен дефолтный счёт (его надо на что-то
  повесить), переименование в одном месте, список для селекта и для LLM, задел
  под остатки по счетам.
- Дефолтный счёт — **флаг `isDefault` на `Account`**, а не `defaultAccountId` на
  `User`. Причина: в API нет эндпоинта `GET /auth/me`, фронту неоткуда прочитать
  поле пользователя, и признак всё равно пришлось бы подмешивать в ответ
  `GET /accounts`. Плата: инвариант «ровно один дефолт» держится кодом, смена
  дефолта идёт через `prisma.$transaction`.
- В транзакции — необязательная ссылка `accountId Int?`.

### Жизненный цикл счетов

- Автосоздания нет. Пока пользователь не завёл счёт — счетов ноль.
- Первый созданный счёт автоматически становится дефолтным.
- Удалить можно любой счёт, включая дефолтный. Транзакциям удалённого счёта
  проставляется `accountId = null` (через `onDelete: SetNull` на уровне БД),
  данные не искажаем и на другой счёт не переносим.
- Удалён дефолтный — дефолтным становится первый по алфавиту из оставшихся.
  Удалён последний счёт — дефолта нет, поле исчезает с экранов.
- Переименование счетов не делаем. Если понадобится — добавим отдельно и сразу
  для категорий тоже, чтобы два похожих экрана не разъезжались.

### Ввод и отображение

- Поле «Счёт» показывается, только если у пользователя есть хотя бы один счёт.
- Ввод — в `AddTransactionDialog`, и при создании, и при правке. При создании
  предвыбран дефолтный счёт, при правке — текущий счёт транзакции (или
  дефолтный, если у неё `null`).
- Пустого варианта в селекте нет: отвязать счёт «в никуда» нельзя.
- В подробной карточке строка «Счёт» рендерится только при `accountId != null`.
  `null` не показываем никак — ни «не указан», ни подставленный дефолт: UI не
  должен выдавать догадку за факт.
- Дефолт подставляет **бэкенд при создании** транзакции, а не фронт при
  отображении. Поэтому `null` остаётся только у исторических записей и у тех,
  чей счёт удалили, а смена дефолта не переписывает историю задним числом.
- Существующие транзакции миграцией не трогаем — у них `accountId = null`.

### Голосовой ввод

- В промпт LLM добавляется список счетов пользователя, модель выбирает строго
  из него.
- Не совпало — подставляем дефолтный счёт. Счетов нет — `null`.
- Новые счета голосом не создаём: ни `suggestedAccounts`, ни pending-логики с
  авто-подтверждением, как у категорий, у счёта нет.

## План работ

### 1. Бэкенд: схема и миграция

`budget-api/prisma/schema.prisma`:

```prisma
model Account {
  id        Int     @id @default(autoincrement())
  title     String
  isDefault Boolean @default(false)
  userId    Int
  user      User    @relation(fields: [userId], references: [id])

  transactions Transaction[]

  @@unique([userId, title])
}
```

В `Transaction`:

```prisma
accountId Int?
account   Account? @relation(fields: [accountId], references: [id], onDelete: SetNull)
```

`onDelete: SetNull` — при удалении счёта Postgres сам обнуляет `accountId` у его
транзакций, вручную `updateMany` не пишем.

Миграция: `npx prisma migrate dev --name add-accounts`. Данные не переносим.

### 2. Бэкенд: модуль accounts

Новые файлы по образцу `src/categories/`:

- `src/accounts/accounts.module.ts`
- `src/accounts/accounts.controller.ts`
- `src/accounts/accounts.service.ts`
- `src/accounts/dto/create-account.dto.ts` — `title`, 1–50 символов

Эндпоинты:

| Метод  | Роут                     | Описание                                                                 |
| ------ | ------------------------ | ------------------------------------------------------------------------ |
| GET    | `/accounts`              | список счетов, сортировка по `title`, с `isDefault` и `transactionCount` |
| POST   | `/accounts`              | создать; первый счёт пользователя становится дефолтным                   |
| PATCH  | `/accounts/:id/default`  | сделать дефолтным                                                        |
| DELETE | `/accounts/:id`          | удалить; дефолтный перевешивается на первый по алфавиту из оставшихся    |

Смена дефолта и удаление дефолтного — через `prisma.$transaction` (снять флаг со
всех счетов пользователя + поставить одному должно быть неделимой операцией).

### 3. Бэкенд: счёт в транзакциях

- `CreateTransactionDto` += `accountId?: number`.
- `TransactionsService.assertAccountOwned(userId, accountId)` — по аналогии с
  `assertCategoryOwned`, чтобы нельзя было привязать чужой счёт.
- `create()`: `accountId` не передан — подставить дефолтный счёт пользователя;
  счетов нет — `null`.
- `update()`: проверка владения счётом (дальше `accountId` уезжает в `data`
  вместе со всем `dto`).

### 4. Бэкенд: голосовой ввод

- `ParsedTransaction` += `account: string | null`.
- Сигнатура `TransactionParser.parse(text, categoryTitles, accountTitles)`.
- `SYSTEM_INSTRUCTION`: поле `account` — строго одно название из списка счетов
  пользователя или `null`, не выдумывать.
- `normalize()` подстраховывает новое поле.
- `createFromVoice()`: тянем счета, сопоставляем без учёта регистра (как сейчас
  категории), не совпало — дефолтный счёт.
- В лог `DEBUG_VOICE` добавить список счетов.

### 5. Фронт: feature accounts

`budget-web/src/features/accounts/`:

- `api.ts` — тип `Account`, `getAccounts`, `createAccount`, `deleteAccount`,
  `setDefaultAccount`
- `keys.ts` — `accountKeys.all`
- `hooks.ts` — `useAccounts`, `useCreateAccount`, `useDeleteAccount`,
  `useSetDefaultAccount`

Структура повторяет `features/categories/`, включая оптимистичное добавление в
кеш.

### 6. Фронт: экран «Счета»

- `src/pages/AccountsPage.tsx`, маршрут `/accounts` в `App.tsx`, ссылка в
  `SettingsPage` рядом с «Категории».
- Добавление счёта, пометка «по умолчанию» у дефолтного, кнопка «сделать
  дефолтным» у остальных, удаление.
- Удаление — с тем же undo-тостом, что на экране категорий, но текст другой: у
  категорий удаление непустых запрещено, здесь разрешено, и в подтверждении
  указываем, сколько транзакций останется без счёта.
- Экран доступен всегда, в том числе при нуле счетов — иначе первый негде
  завести.

### 7. Фронт: диалог и карточка

- `AddTransactionDialog` — селект «Счёт» последним полем, рендерится только при
  `accounts.length > 0`.
- `TransactionDetailPage` — строка «Счёт» в списке подробностей только при
  `tx.accountId != null`, название резолвится через `useAccounts` тем же `find`,
  что сейчас для категории.

### 8. Документация

- `budget-api/SPEC.md` — файлы модуля `accounts`, модель `Account` и поле
  `accountId` в разделе схемы Prisma, четыре строки в таблице `API Routes`,
  правка описаний изменившихся файлов (`transactions.service.ts`, DTO, парсеры).
- `budget-web/SPEC.md` — `features/accounts/*`, `AccountsPage.tsx`, строка
  `/accounts` в таблице `Routes`.
- Корневой `README.md` — пункт про счета в соответствующем этапе + дата
  обновления.

Спеки правятся в том же коммите, что и код.

## Порядок работ

1. Бэк: модель, миграция, модуль `accounts`
2. Бэк: `accountId` в транзакциях и подстановка дефолта
3. Бэк: счёт в промпте LLM и в `createFromVoice`
4. Фронт: feature + экран «Счета»
5. Фронт: селект в диалоге и строка в карточке

      `accountId = null`.
- [ ] Завёл первый счёт — он дефолтный, поле появилось в диалоге и в новых
      карточках; старые траты остались без строки «Счёт».
- [ ] Создал трату, счёт не выбирал — приехал дефолтный.
- [ ] Сменил дефолт — старые транзакции не переехали.
- [ ] Голосом «кофе 300 рублей с Тинькофф» — счёт распознался; без упоминания
      счёта — приехал дефолтный.
- [ ] Удалил счёт с транзакциями — транзакции живы, строка «Счёт» у них
      пропала; если удалял дефолтный, дефолтным стал следующий.
- [ ] Удалил все счета — поле исчезло отовсюду, ошибок нет.
