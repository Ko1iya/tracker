# CLAUDE.md

Инструкции для Claude Code при работе с каталогом `budget-api` монорепозитория Tracker.
Общие правила проекта — в корневом `../CLAUDE.md`.

## О проекте

`budget-api` — бэкенд учебного пет-проекта **Tracker: AI Budget App** (приложение для учёта личного бюджета с голосовым вводом расходов через AI). Цель пользователя — разобраться, как устроен фулстек; промышленная готовность не приоритет. План этапов разработки — в корневом `../README.md`.

Стек: **NestJS** + **Prisma** + **PostgreSQL** (в Docker). Дальше будут JWT-авторизация, OpenAI Whisper/LLM, React-фронт, Capacitor для мобилки.

## Поддержка SPEC.md

В корне репозитория лежит **`SPEC.md`** — живая спецификация структуры проекта. Это главный артефакт, который должен оставаться синхронным с кодом.

### Когда обновлять

Обновляй `SPEC.md` **в том же ответе**, что и изменение кода, если ты:
- создал, удалил, переименовал или переместил файл в `src/`;
- изменил публичный API файла (экспорты, методы класса, поля DTO);
- изменил `prisma/schema.prisma` (добавил/удалил модель, поле, связь);
- изменил `docker-compose.yml`.

Если правка чисто внутренняя (рефакторинг приватной функции без изменения смысла файла) — `SPEC.md` можно не трогать.

### Что должно быть в SPEC.md

**Только две секции верхнего уровня:**

1. **`## Project Structure`** — ASCII-дерево репозитория + краткие описания каждого файла (2–4 строки: назначение + ключевые экспорты/методы). Для `prisma/schema.prisma` — подсекция со списком моделей и их полей. **НЕ описывай** `node_modules/`, `dist/`, `test/`, `eslint.config.mjs`, `tsconfig*.json`, `nest-cli.json`, `prisma.config.ts`, `package*.json`, `.env`. Описывай только: `src/**`, `prisma/schema.prisma`, `docker-compose.yml`.
2. **`## API Routes`** — таблица всех HTTP-эндпоинтов: Method, Route, Описание, Файл, Статус.

**НЕ добавляй** разделы Overview, Tech Stack, Changelog, Dependencies, How to Run и т.п. — пользователь явно отказался от них.

### Стиль описаний

- **Язык:** русский для описаний, английский для технических терминов и имён сущностей. Пример: `TransactionsService — слой бизнес-логики для CRUD транзакций`.
- **Длина:** 2–4 строки на файл. Назначение + ключевые экспорты/методы.
- **Зависимости между файлами:** упоминай **только внешние интеграции** (Prisma, OpenAI, S3 и т.п.). Внутренние импорты не дублируй — это видно в коде.
- **Удаления:** при удалении/переименовании файла убирай его из спеки без следа. Changelog не ведём — история в git.

### Если не уверен в назначении файла

Не выдумывай. Задай пользователю короткий уточняющий вопрос: «Не понял назначение `X.ts` — опишешь одной строкой?»

### При первом запросе на изменение SPEC.md в сессии

Прочитай актуальный `SPEC.md` целиком, прежде чем редактировать — чтобы не сломать существующие описания соседних файлов.

## Общие правила работы

- Пользователь — фронтенд-разработчик, делающий **первый фулстек-проект**. Бэкенд-концепции (DI, guards, DTO, миграции, ORM) объясняй подробнее, чем фронтенд. Аналогии с React/фронтом приветствуются.
- Между сессиями бывают большие паузы. Если пользователь возвращается, можно коротко напомнить, на каком этапе остановились (по `../README.md` и `SPEC.md`).
- План разработки лежит в корневом `../README.md` — там же отмечен текущий этап (Этап 6: Релиз).
