# CLAUDE.md

Инструкции для Claude Code при работе с этим репозиторием.

## О проекте

`budget-web` — фронтенд учебного пет-проекта **Tracker: AI Budget App** (приложение для учёта личного бюджета с голосовым вводом расходов через AI). Цель пользователя — разобраться, как устроен фулстек; промышленная готовность не приоритет. План этапов разработки — в `README.md` (текущий — Этап 2: Frontend MVP).

Стек: **React 19** + **Vite** + **TypeScript**. Дальше будут Tailwind CSS, React Router, TanStack Query (связь с `budget-api` по REST), затем голосовой ввод (`MediaRecorder`) и Capacitor для мобилки.

Бэкенд лежит в соседнем репозитории `budget-api` (NestJS + Prisma + PostgreSQL), дев-сервер фронта `http://localhost:5173` уже прописан в его CORS.

## Поддержка SPEC.md

В корне репозитория лежит **`SPEC.md`** — живая спецификация структуры проекта. Это главный артефакт, который должен оставаться синхронным с кодом.

### Когда обновлять

Обновляй `SPEC.md` **в том же ответе**, что и изменение кода, если ты:
- создал, удалил, переименовал или переместил файл в `src/`;
- изменил публичный API файла (экспортируемый компонент, его props, экспортируемые хуки/функции/типы);
- добавил, удалил или переименовал страницу/маршрут (React Router);
- изменил `index.html` или `vite.config.ts` так, что это влияет на структуру приложения.

Если правка чисто внутренняя (рефакторинг разметки/стилей внутри компонента без изменения его props и назначения) — `SPEC.md` можно не трогать.

### Что должно быть в SPEC.md

**Только две секции верхнего уровня:**

1. **`## Project Structure`** — ASCII-дерево репозитория + краткие описания каждого файла (2–4 строки: назначение + ключевые экспорты/props/хуки). **НЕ описывай** `node_modules/`, `dist/`, `public/`, `eslint.config.js`, `tsconfig*.json`, `package*.json`, `.gitignore`, `.env*`. Описывай только: `src/**`, `index.html`, `vite.config.ts`.
2. **`## Routes`** — таблица клиентских маршрутов (React Router): Path, Страница/компонент, Описание, Файл, Статус. Пока роутинг не настроен — секция содержит пометку об этом.

**НЕ добавляй** разделы Overview, Tech Stack, Changelog, Dependencies, How to Run и т.п. — пользователь явно отказался от них (как и в `budget-api`).

### Стиль описаний

- **Язык:** русский для описаний, английский для технических терминов и имён сущностей. Пример: `App — корневой компонент, монтирует роутер`.
- **Длина:** 2–4 строки на файл. Назначение + ключевые экспорты/props.
- **Зависимости между файлами:** упоминай **только внешние интеграции** (вызовы API `budget-api`, браузерные API вроде `MediaRecorder`, сторонние сервисы). Внутренние импорты не дублируй — это видно в коде.
- **Удаления:** при удалении/переименовании файла убирай его из спеки без следа. Changelog не ведём — история в git.

### Если не уверен в назначении файла

Не выдумывай. Задай пользователю короткий уточняющий вопрос: «Не понял назначение `X.tsx` — опишешь одной строкой?»

### При первом запросе на изменение SPEC.md в сессии

Прочитай актуальный `SPEC.md` целиком, прежде чем редактировать — чтобы не сломать существующие описания соседних файлов.

## Общие правила работы

- Пользователь — фронтенд-разработчик, делающий **первый фулстек-проект**. Фронтенд-концепции (React, Vite, компоненты, хуки) объяснять подробно не нужно. А вот всё, что касается связи с бэкендом (CORS, JWT в заголовках, формат ответов API), стоит пояснять подробнее.
- Между сессиями бывают большие паузы. Если пользователь возвращается, можно коротко напомнить, на каком этапе остановились (по `README.md` и `SPEC.md`).
- Tailwind CSS планируется к установке на следующем шаге — пока стили обычным CSS.
